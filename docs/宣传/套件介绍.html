The Pain Points

传统数模工作流的三大难题

🔀

① 交接割裂

建模、编程、论文三个环节通常是三个人各干各的，最后靠人肉对文档拼装：

  • 论文手拿不到可复现的结果与图表
  • 编程手对模型的假设理解走样
  • 交接没有固定产物契约，经常返工
👁️

② 看图靠猜

很多主模型不支持图像输入（read_image 拒读）：

  • 图表是否空白、遮挡、缺坐标轴标签？看不到
  • 图与正文结论是否一致？只能靠猜
  • 出图质量没有客观检查手段
🧠

③ 自审盲区

同一个模型既生产又验收，天然缺乏批判距离：

  • 编造的数值/来源自己发现不了
  • 口径不自洽、推荐前后矛盾
  • "自己审自己"形同虚设
结果是：质量看运气，论文靠熬夜，返工无底洞。

    每个门禁查什么

    门禁检查内容
    M1 建模终检题目要求是否全部有对应模型/方案；子问题有无遗漏；约束与评价口径是否正确
    P1 最小可运行全量计算前先跑通最小可运行代码，确认能出真实结果
    P2 编程终检所有子问题都有真实运行结果与图表；数字有源；复现清单完整
    W1 证据大纲论文结构每章都有证据支撑（哪张图/表/结论），无孤立结论
    W2 论文终检公式与结果一致、无空表空图、图表覆盖全部子问题、编号引用连续、参考文献双向对应、符合官方格式
  • 有界迭代：单轮评审最多 2 轮修复；预算耗尽输出 decision_memo，绝不无限打磨
  • FAIL 必须按证据回退：主模型不得口头覆盖失败结论；被审产物实质变化时相关 PASS 立即失效
  • 评审严重度分级：blocker / high / medium / low，各自有处置规则
    • Two Superpowers

    看图，和独立挑错

    🖼️

    识图子代理（全局 skill）

    主模型读不了图？用 workflow 派生一个指定视觉模型的子代理替它看：

    • 探测：llm 服务找 inputModalities 含 image 的模型（不硬编码）
    • 派发：agent(prompt, { provider, model }) 指定视觉模型
    • 检查：空白 / 遮挡 / 缺坐标轴标签 / 缺图例 / 是否支撑结论
    • 输出：PASS / FAIL + 缺陷与建议

    已验证候选：opencode-go/mimo-v2.5、kimi-coding/k3 等

    ⚔️

    独立模型审查（对抗式评审）

    用与产出方不同厂商的模型做独立评审，跳出主模型自审盲区：

    • 事实性：headline 数值能否溯源到 results/ 与图表？有无编造？
    • 一致性：口径/符号/结论在报告、代码、结果、图之间自洽？
    • 完备性：是否覆盖全部子问题？有无遗漏约束？
    • 引用核验：参考文献真实存在且被正确引用？
    • 独立判断：通过/不通过 + 严重度 + 必须修复的证据项

    本环境推荐：kimi-coding/k3-256k（26 万上下文，text+image）

    识图看"视觉"，独立审查审"内容"——两者可组合：先识图，再对抗式挑错。
